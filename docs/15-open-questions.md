# 已确认决策与剩余待确认项

本文件把已由产品负责人确认的边界与仍需实现前确定的契约分开。已确认项不应在后续文档中重新描述成开放问题。

## 1. 已确认

| 决策 | 已确认结论 | 设计影响 |
|---|---|---|
| 产品名称 | `Sales Platform（销售平台）` | 仓库、API、事件与客户输出统一使用该名称 |
| 系统边界 | Sales Platform 是 BMS/CRM 之外的独立系统 | 不把平台业务数据写入 BMS/CRM 领域表 |
| 打开平台时的身份 | 使用 BMS 认证 | BMS 后端提供认证/权限交互适配；Sales Platform 不保存 BMS 口令 |
| 项目来源 | Sales Platform 自己创建项目 | 不要求关联现有销售项目、报价或 CRM 项目 ID |
| 前端边界 | React + Electron；前端计划放在独立仓库 | 本设计仓库保留契约；最终仓库名和 CI/CD 待建立 |
| 桌面首发 | Windows 与 macOS 同一首发批次 | 共享 React UI，但安装、签名、更新和本地能力分别验收 |
| 初步客户文件 | 可在现场交给客户，不需要工艺工程师参与 | 文件仍标明未经工艺审核，不可冒充正式方案 |
| 初步文件审核 | 必须由被授予专用审核权限的指定人员审核 | 使用逻辑权限 `customer.handout.review`；不绑定“团队负责人”等职级 |
| 客户输出格式 | PDF 与 Word（DOCX） | 两种文件从同一冻结 manifest 生成并保存 checksum |
| 客户输出语言 | 中文、英语、俄语、乌克兰语 | 分别使用 `zh-CN`、`en`、`ru`、`uk`，俄语与乌克兰语不得合并成一个版本 |
| LLM | Phase 1 加入受控实验 | 用于提取、翻译/说明草稿和候选建议；不得直接发布工程事实或最终选型 |
| 数据维护权限 | 设专用权限维护系统数据 | 逻辑权限为 `sales_platform.data_maintain`，高风险发布仍执行提议/审核/发布分离 |
| 企业展示更新 | 使用结构化多语言 CMS，不写死在 React/Electron | 共享页面结构、四语言翻译、媒体库、不可变 ContentRelease、ETag/离线缓存 |
| 时区 | 必须支持不同使用地时区 | 数据库存 UTC；项目、用户和会谈保存 IANA 时区，界面/文件显示当地时间及 UTC 偏移 |
| BMS 内部管理入口 | 使用 `Sales Platform 管理中心` 控制面 | BMS 菜单/权限/BFF 展示平台投影；不复制领域表、不直接 SQL，深度工作台仍在独立平台 |
| BMS 菜单与路由 | “审核与发布”合并；“权限与集成”改为“权限”；不设“审计与运行” | 所有新增页面/表格列表由菜单管理配置并动态生成路由，禁止写死 `routes.ts` |
| 非标准产品 Excel | 任何 XLSX 均可进入结构发现/映射流程，但不能盲目自动发布 | 多区域、Mapping Profile、确定性标准化、字段 diff、人工审核和新规格版本发布 |
| Sales Platform 数据落点 | 121 服务器的 `kj_sale_platform` | 项目、内容、设备、导入、推荐、审核与发布数据统一归 Sales Platform；BMS 数据不得混入该 schema |
| BMS 数据落点 | 暂时保留在 BMS DEV，后续按转移包进入 BMS PROD | 菜单、角色、权限和 BFF 映射保存在 BMS 自己的数据库；转移 SQL 保存在 `integrations/bms/` |

## 2. 实现前必须确认

1. BMS 认证采用哪种 token 验证/交换方式、测试环境地址、退出登录和过期刷新契约是什么？
2. 已确认菜单名称和合并关系后，各页面编码、跳转路径，以及逻辑权限（包括 `customer.handout.review` 与 `sales_platform.data_maintain`）对应的 `functionCode` 是什么？
3. Sales Platform 业务后端最终部署为独立 Node.js 服务、BMS 后端旁的独立服务，还是其它运行单元？无论选择哪一种，领域 schema 与模块边界保持独立。
4. 前端独立仓库的正式仓库名、发布流水线、Windows/macOS 签名证书和自动更新渠道是什么？
5. 首批矿种、工艺段、设备类型与强制红线规则是什么？
6. 首批金标准案例和可用源文件由谁提供、何时可用？当前已确认用户稍后提供，不应虚构文件内容。
7. 谁是工艺规则 Owner、设备数据 Owner、内容/翻译 Owner 和正式工程发布人？
8. LLM 供应商/模型、数据驻留、敏感文档是否允许出域、成本预算和评测基线是什么？
9. 121 的实际 MySQL 版本、排序规则、时区、备份/RPO 和账号权限基线是什么？
10. 内容编辑、四语言审核、媒体权利审核和 Content Publisher 分别由谁承担？第一批页面/图片和使用权证明何时提供？
11. 媒体对象存储/CDN 是否必须在公司控制环境；公开公司网站未来是否也复用这一 CMS？
12. BMS BFF 归属哪个后端模块，第一批先上线内容/handout 还是设备/规则治理？
13. 同型号不同图号是不同销售配置、历史设计版本，还是需要由文件/产品类型分别判断？
14. `参考重量`、`报价重量`、`运输重量` 的正式定义与优先级是什么？底价/报价是否属于 Sales Platform？

## 3. Phase 1 内可以细化

- 初步文件审核是否允许在极端情况下自审。当前默认制作者与审核人必须是不同主体。
- 中文、英语、俄语、乌克兰语的翻译工作流、术语表和免责声明法务版本。
- PDF 与 DOCX 的模板版式、是否需要客户签字、二维码和离线校验页。
- LLM 首批实验范围在“文档提取、翻译草稿、说明草稿、候选建议”中的启用顺序。
- 是否已有公司统一对象存储、Redis、监控、LLM Gateway 和签名更新服务。
- 项目时区默认取用户时区、矿山所在地还是销售手工选择；建议创建项目时明确选择矿山所在地 IANA 时区。
- 四语言是否必须同批发布。建议每个 locale 可继续沿用上一已发布版本，但任何 locale 都不能回退到草稿或静默混用其它语言。
