# 产品需求说明（PRD）

## 1. 产品定位

Sales Platform 是 BMS/CRM 之外的独立系统，以“销售看板”承载完整客户会谈：企业与海外子公司展示、平台内建项目、引导式矿山问诊、候选工艺与每段多设备推荐、销售现场选择、权限审核后的初步打印件和工程交接。随后由工艺工程师深化、校核、审核并形成正式方案。产品不是自动详细设计工具，而是客户沟通—销售方案—工程协同与知识复用平台。

## 2. 用户与核心价值

| 用户 | 当前问题 | 平台价值 |
|---|---|---|
| 销售 | 信息采集不一致、等待工程师、难解释方案 | 结构化问卷、候选场景、缺失信息提示、可读技术方案 |
| 内容编辑/翻译 | 改字换图依赖开发、四语言容易不同步 | 结构化页面编辑、媒体库、翻译矩阵、预览与发布回滚 |
| 初步打印审核人 | 现场资料必须有人检查，但不应绑定具体职级 | 按专用权限审核冻结的语言/文件版本并批准或退回 |
| 客户（旁观/沟通对象） | 不清楚公司能力、需求问题零散、带走材料不一致 | 演示模式、引导问诊、初步流程图与设备清单、明确适用边界 |
| 工艺工程师 | 历史资料分散、重复画流程、修改无追溯 | 案例复用、图形化深化、自动校核、差异与版本 |
| 审核人 | 看不清依据和变更 | 规则/案例/设备版本、差异、风险、批准留痕 |
| 数据管理员 | 设备与案例更新随意 | 提议—校验—审核—发布、质量问题、复核日程 |
| 管理者 | 不知道算法是否可靠 | 覆盖率、采用率、人工改动率、失败与回退原因 |

## 3. 核心用户故事

### 企业展示与会谈启动

- 作为销售，我能用客户演示模式展示公司、乌兹别克斯坦子公司、生产/服务能力、产品功能和授权案例。
- 展示内容由后台版本化管理，客户模式不出现内部导航、其他客户、规则原文或内部评分。
- 作为内容编辑者，我能用固定区块修改文字、图片和排序；作为翻译/审核人，我能按 locale 处理缺失或过期字段并查看桌面/窄屏客户预览。
- 图片只上传一次即可复用，系统保存 checksum、尺寸、焦点、版权/客户授权和派生格式；图片含文字时可设置 locale 专用版本。
- 发布形成不可变 ContentRelease；Web/Electron 自动更新已发布内容，失败或离线时保持上一完整版本，不因换图改字重新发安装包。
- 我能从展示页直接在 Sales Platform 新建项目和客户沟通会话，并记录展示语言、IANA 时区和使用的内容版本。

### 销售需求采集

- 作为销售，我能在 Sales Platform 创建项目，不依赖现有 BMS/CRM/报价项目 ID，并填写矿石、产能、产品目标、泥/水、场地、道路、电力和扩产要求。
- 系统把模糊项转成可测字段，并明确显示必填、建议补充和未知。
- 提交前系统给出完整度、冲突和“必须先做试验/人工确认”的提示。

### 自动推荐

- 作为销售，我能针对一个不可变输入快照发起推荐。
- 系统返回 1–N 个候选场景，而不是只有一个黑盒答案。
- 每个候选显示工艺图、分段设备、数量、能力余量、理由、排除项、风险和缺失信息。
- 推荐失败时显示确定原因，不用“AI 失败”掩盖数据或规则问题。

### 销售选择与工程深化

- 作为销售，我能选择候选方案，并在每个工艺段比较多个设备型号、数量、能力、运输和选择理由。
- 系统创建独立销售方案修订，不改变算法候选原件，也不提前冒充工程修订。
- 我能在备选设备间切换，调整总数/运行/备用数量；任何调整都会重新校核并记录差异。
- 我能冻结中文、英语、俄语或乌克兰语的 PDF/DOCX 初步文件并提交专用权限审核；审核通过后才能现场打印或交付客户。
- 作为持有 `customer.handout.review` 权限的审核人，我能查看具体 manifest、语言、PDF/DOCX 和免责声明版本，批准或退回；我不需要是工艺工程师或固定职级。
- 我能把问答、输入快照、算法候选、销售修改、客户偏好和打印件一并提交工艺工程师。
- 作为工艺工程师，我能增删/改工艺节点和物流，调整设备类型、型号、数量、运行/备用配置和说明。
- 系统持续检查图连接、循环标记、能力、运输、电力、水量和必需工艺段。
- 工程师提交时必须解释关键偏离，例如替换算法设备、忽略警告或修改产能裕量。

### 审核与销售发布

- 作为审核人，我能查看算法原稿与工程修订差异、未关闭警告、输入/依赖版本和工程师说明。
- 批准后能生成不可变销售技术方案包。
- 销售看到的版本明确标注有效状态、发布日期、适用假设和是否已被替代。
- 客户需求变更时，从旧方案分支新修订，不覆盖历史交付物。

### 数据更新

- 原始 PDF/Excel/图片进入暂存区；Phase 1 即试用 LLM 做提取、字段映射、翻译/说明草稿和候选建议，但只能产生候选事实或辅助草稿。
- 数据管理员/工程师比较原值、新值、来源和影响范围后再发布。
- 设备规格、规则和案例新版本发布后，旧推荐保持不变，只标记可能受影响并允许重跑。

## 4. 功能范围

### MVP 必须有

- 结构化企业展示 CMS、媒体库、四语言翻译/审核矩阵、预览、发布/回滚和客户演示模式
- 客户沟通会话与版本化引导问卷
- 项目需求问卷与输入快照
- 矿石/工艺/设备/单位主数据
- 历史案例与流程图
- 设备型号、规格版本与能力包络
- 结构化硬约束和规则测试
- 候选方案生成与解释
- 每个工艺段多个设备备选及一致字段比较
- 销售方案修订、设备切换和现场初步打印件
- 初步打印件的权限型审核、PDF/DOCX 和四语言版本
- 销售方案提交工艺工程师与差异交接
- 流程图编辑器和设备配置
- 工程审核、批准和销售发布
- PDF + DOCX 客户输出；JSON manifest/API 作为系统内部与集成事实
- 审计日志和版本差异
- 数据导入暂存、审核、发布
- Phase 1 受控 LLM 实验及模型/prompt/输入/输出/人工处置记录
- Windows + macOS 同批次 Electron 交付与时区显示

### 后续范围

- 扩大 OCR/LLM 批量范围并按首期评测结果优化
- 高级物料/水量平衡
- 价格/交期与商务优化
- 实际运行数据自动回流
- 更多语言与术语自动化工作流
- 多目标数学优化器
- 图数据库或独立向量服务（有规模证据后）

## 5. 关键业务规则

1. 未发布的数据不得参与正式推荐。
2. 每次推荐锁定输入和依赖版本。
3. 硬约束失败的候选不能靠评分进入结果。
4. 自动候选不能直接成为正式方案；销售冻结的初步客户文件必须经 `customer.handout.review` 权限审核后才能交付，并带醒目免责声明。
5. 销售方案不能伪装为工程批准版本；正式发布前至少经过工艺工程师提交和指定审核人批准。
6. 已发布方案、规则、设备规格和案例版本不可原地修改。
7. 所有人工覆盖警告必须填写原因并进入审计。
8. 缺乏关键试验数据时，结果必须降级或停止，并明确要求补充。
9. LLM 输出不得直接写入已发布工程事实、绕过设备/规则校核或执行审核动作。
10. 所有业务时间保存 UTC；项目/会谈/用户保留 IANA 时区，客户文件显示当地时间、时区和 UTC 偏移。

## 6. 非功能目标（初始）

- API 常规读请求 P95 < 500 ms（不含大图/附件）。
- 推荐任务在 MVP 数据规模下 P95 < 60 s，异步执行并可观察阶段进度。
- 流程图编辑在 200 节点/500 边以内保持流畅。
- 发布操作强一致，重复请求不得生成两个正式版本。
- 关键变更 100% 留审计；推荐 100% 可复现到依赖版本。
- 生产环境月可用性目标 99.5%（MVP，可评审调整）。

## 7. 成功指标

- 销售需求一次采集完整率
- 销售会谈完成率、平均问诊时长和初步打印成功率
- 客户会谈到工程交接的完整记录率
- 推荐覆盖率与“需人工设计”比例
- 候选被销售选择率
- 销售设备替换率、超出推荐清单比例和工程师回改率
- 算法候选到工程终稿的节点/设备改动率
- 工程师平均准备时间下降比例
- 审核退回率及原因
- 发布方案被后续替代的原因分布
- 数据质量问题关闭时间
- 实际运行反馈覆盖率

这些指标用于发现系统边界和数据不足，不用单一“推荐命中率”掩盖工程安全问题。
