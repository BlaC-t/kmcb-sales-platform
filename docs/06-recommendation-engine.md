# 推荐引擎设计

## 1. 目标

推荐引擎输出候选，不输出未经工程审核的最终设计。它必须是确定性优先、可解释、可复现和可回退的混合系统。

Phase 1 同时开展 LLM 辅助实验。LLM 可以提出字段映射、缺失问题、流程/设备候选和说明草稿，但候选必须重新进入相同的硬约束、图校验、设备能力和证据链；模型文本不能成为跳过这些步骤的“最终答案”。

## 2. 五层模型

### Layer 1：输入归一化

- 统一单位、同义词和分类编码。
- 计算 `design_tph = tpd / operating_hours / availability × margin` 等派生事实。
- 区分未知、客户未提供、不适用和零值。
- 生成缺失/矛盾清单和数据完整度。

### Layer 2：硬约束与必需工艺

规则效果：

- `REJECT`：排除流程或设备。
- `REQUIRE`：必须加入工艺段、附件或人工检查。
- `WARN`：保留但需要工程确认。
- `PREFER`：只影响排序。

示例仅为结构说明，正式规则需工艺团队发布：

```json
{
  "code": "LOGISTICS-001",
  "when": {
    "fact": "equipment.shippingWeightT",
    "operator": "greaterThan",
    "valueFrom": "project.logistics.bridgeLoadLimitT"
  },
  "then": {
    "effect": "REJECT",
    "message": "设备运输重量超过桥梁限重"
  }
}
```

规则 DSL 不允许 `eval`、任意 SQL 或任意 JS。允许的 fact path、operator、value type 和 action 均白名单化。

### Layer 3：相似案例检索

结构化特征优先：

```text
矿种/矿物学、产能对数、给料粒度、硬度、磨蚀性、含泥/含水、
湿式/干式、目标产品、供水/电力、海拔、运输限制、工艺目标
```

相似度示例：

```text
S_case = Σ(weight_i × similarity_i × quality_i × availability_i)
```

- 类别用层级/集合相似度。
- 连续值用归一化距离或区间覆盖。
- 未知字段不当成 0，而是降低证据覆盖率。
- 文本 embedding 仅作补充召回，不能越过结构化硬约束。
- 案例数据质量、投产验证和来源可靠性影响权重。

### Layer 4：流程与设备候选

1. 从已发布工艺模块模板和高质量案例提取候选子图。
2. 根据 REQUIRE 规则补入必需节点。
3. 检查端口兼容、输入输出、循环与终端产品。
4. 用粗平衡计算各节点设计流量。
5. 先选择设备类型，再为每个工艺段筛选并排序 1–N 个具体规格版本。
6. 对每个设备选项计算建议数量：运行数、备用数、利用率和能力裕量。
7. 应用给料粒度、产品粒度、湿/干式、物性、运输、电力、场地、吊装和维护约束。

### Layer 5：多场景评分与解释

评分仅对通过硬约束的候选：

```text
total =
  technical_fit
  + historical_evidence
  + reliability
  + operability
  + logistics_fit
  + sustainability
  + future_expandability
  - uncertainty_penalty
  - warning_penalty
```

权重按场景版本化：平衡、低投资、高可靠、低水耗、低能耗、扩产、运输受限。没有可信价格/能耗数据时，不生成伪精确分数。

## 3. 输出模型

每个候选方案包含：

- 工艺图节点/边；
- 每段目的、输入输出、关键参数；
- 每个工艺段的设备类型及多个型号选项；
- 每个选项的建议数量、运行/备用、能力、余量、适用条件、排序理由和工程确认状态；
- 总分与分项分数；
- 命中规则与未通过警告；
- 相似案例及相似字段；
- 推荐理由、排除设备/流程及原因；
- 假设、缺失信息、必须试验/人工确认项；
- 全部依赖版本。

“可信度”不是模型自信数字，应由证据覆盖率、数据质量、规则覆盖、案例质量和校核状态组成，并展示分解。

## 3.1 Phase 1 LLM 实验支路

```text
结构化输入/已审核证据
  → 受限 prompt/template
  → LLM 候选或草稿
  → schema 校验
  → 硬约束/图/设备能力校核
  → 人工接受、修改或拒绝
  → 指标与误差样本
```

每次运行保存 purpose、provider/model、prompt/template 版本、输入 checksum、输出、token/成本、延迟和人工处置。默认实验开关可关闭；LLM 不可用时确定性推荐仍正常工作。敏感数据是否允许发送到外部 provider 由数据出域策略决定。

## 4. 图校验

运行时用 `MultiDirectedGraph`：

- 所有非端点节点至少有入边和出边；
- 端口类型兼容；
- 循环边显式标记且属于允许的回路模式；
- 终端流类型完整（精矿、尾矿、回水等）；
- 节点处理能力覆盖入料；
- 不把画布坐标当作顺序；
- 计算/遍历设置最大步数，避免异常循环。

## 5. 规则测试

每条规则至少有：

- 应命中案例；
- 不应命中案例；
- 边界值；
- 缺失事实；
- 单位转换；
- 与高优先级规则冲突；
- 解释模板期望。

规则集发布前跑回归案例，比较候选数量、淘汰原因和最终场景差异。差异超阈值需人工批准。

## 6. 评估框架

### 离线

- 历史金标准 Top-K 流程模块召回率
- 设备类型/型号 Top-K 覆盖
- 硬约束违规数（目标为 0）
- 工程师从候选到终稿的编辑距离
- 解释完整率与证据可用率
- 不同规则/目录版本的回归差异

### 在线

- 销售候选选择率
- 销售在推荐设备间切换的比例、超出推荐清单比例
- 销售选择到工程终稿的设备一致率/改动率
- 工程审核通过/退回率
- 平均完成时间
- 人工覆盖警告率
- 发布后需求变更/技术纠正率
- 运行反馈与推荐偏差

## 7. 安全回退

满足以下任一条件返回“需要人工设计”，而不是强行推荐：

- 关键矿石/试验数据缺失；
- 无任何通过硬约束的流程；
- 首批白名单外矿种/工艺；
- 规则冲突无法自动解析；
- 设备能力数据过期或无可信来源；
- 粗平衡不收敛或循环异常；
- 物流/电力/水/场地约束不足以判断。

## 8. 包选择

- Graphology：适合运行时有向多重图；数据库仍是事实源。
- `json-rules-engine`：可作为受限 JSON 规则执行器，但需封装允许的事实、操作符、版本和解释，不直接向用户暴露其全部能力。
- 独立向量检索服务：只在文本/描述补充召回有明确评测收益时启用；它不是 121 MySQL schema 的默认组成部分。
- BullMQ：用于推荐阶段任务和重试；不可替代数据库状态机和 Outbox。
